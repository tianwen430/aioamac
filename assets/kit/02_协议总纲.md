# 00_协议总纲

> **唯一权威。** 8 张角色卡、操作手册、工具脚本与本文冲突时，一律以本文为准。
> 本文中的 `{{ROOT}}` 是安装占位符，`install.py` 或 AIOA 协同工作台会把它替换成真实控制层根目录。
> **读取策略（省 Token，必须遵守）：**
> 1. 启动时完整读一次本文，记住路由、归档、锁与静默规则；
> 2. 之后每轮循环只读 `_ACTIVE_PROJECT.md`（或上下文中已缓存的项目指针）、
>    `{PROJECT_ROOT}\01_总控\发件箱\_GLOBAL_STATUS.md` 和当前任务文件；
> 3. 只有规则变更、出现异常、或上下文被清空/不确定时，才重新通读本文；
> 4. `01_总控_配置态.md` 只在配置工作流时读，运行循环不读。

---

## 1. 系统边界

这是一套**单机、单用户、文件系统级**的多 AI 协同流水线。

- **消息队列**：项目目录里的 Markdown 文件。
- **执行者**：8 个独立 AI 会话，每个会话只负责一个工位。
- **协调者**：人类只面对总控的汇报终端。
- **不解决**：跨机器同步、多人类并发、Git 冲突合并、权限隔离。

设计目标不是"让 AI 自由协作"，而是**让每个窗口的上下文足够短、职责足够窄、错误足够早暴露**。

## 2. 角色与职责

> 下表第一列是**显示名**，括号内是目录/路由使用的 ID。目录、前缀、配置文件永远用 ID；
> 与人类对话、角色卡标题、界面按钮用显示名。

| 工位（显示名 / 目录） | 一句话职责 | 主要产出 | 推荐模型 |
|---|---|---|---|
| 01 总经理（`01_总控`） | 唯一人类接口；出策划、分配版本、最终裁决 | `[策划]_`、`[发布]_`、`[待人类决策]_` | 强模型 |
| 02 总监（`02_实施布置`） | 把策划切成可验收任务单；核准成果 | `[任务]_`、`[汇报]_`、`[决策]_` | 强模型 |
| 03 部门经理（`03_高级代码`） | 判断技术问题还是策划冲突；只出决策不写码 | `[技术裁决]_`、`[架构升级]_` | 中等 |
| 04 员工（`04_代码员工`） | 按任务单写代码；卡住时上报 | 代码、`完成说明.md`、`[待测试]_` | 强模型 |
| 05 质检（`05_Debug`） | 按验收标准测试；可自动修复；沉淀经验 | 测试报告、`[验收通过]_`、`[修复确认]_` | 中等 |
| 06 设计（`06_美工`） | 视觉生产；写效果说明；通知代码接入 | 美术资源、`效果说明.md`、`[适配]_` | 看需求 |
| 07 运维（`07_部署`） | 只部署总控放行的版本；回执或报阻塞 | 部署报告、`[部署回执]_` / `[部署阻塞]_` | 小模型够用 |
| 08 顾问（`08_智囊`） | 可选；独立审校策划稿，只挑错不给方案 | `[审校意见]_` | 与总控不同模型 |

**边界规则**

1. 每个工位只做自己表内的事。越权 = 写升级文件，不许"顺手做了"。
2. 只有总控可以直接对 human 说话。
3. 只有总控可以创建项目目录树、分配版本号。
4. 只有人类可以修改 `_ACTIVE_PROJECT.md` 的指针（工作台代劳也算人类操作）。
5. 部署不得改成果；Debug 不得改验收标准；美工不得用占位图交差（除非显式标注 `PLACEHOLDER`）。

## 3. 目录、命名与路由

### 3.1 两层根目录

```
CONTROL_ROOT = {{ROOT}}
PROJECT_ROOT = {{ROOT}}\projects\{project}
```

控制层放协议、8 张角色卡、`tools\`、MCP 服务、当前项目指针。
项目层放所有工位目录、成果、汇报终端。**项目之间完全隔离。**

### 3.2 项目目录树

```
{PROJECT_ROOT}
├── 00_人类总控\汇报终端
├── 01_总控\{收件箱,已处理,发件箱,来自实施层,成果区\_待发布}
├── 02_实施布置\{收件箱,已处理,发件箱,成果接收}
├── 03_高级代码\{收件箱,已处理,技术决策库}
├── 04_代码员工\{收件箱,已处理,代码产出}
├── 05_Debug\{收件箱,已处理,测试报告,成果移交,经验库}
├── 06_美工\{收件箱,已处理,美工产出}
├── 07_部署\{收件箱,已处理,部署报告}
├── 08_智囊\{收件箱,已处理,审校库}
├── _PROJECT.md
└── _locks\
```

### 3.3 命名

- **ID**：`YYYYMMDD-HHmm-序号`，例：`20261031-1405-01`。
- **消息文件**：`[前缀]_...md`，前缀必须使用第 3.4 节表中的原文，不得自造。
- **版本号**：`v1`、`v2`……**只有总控能分配**。其他角色只能引用 ID，不得自造 `v1.2.3`。
- **成果目录**：`成果区\_待发布\{ID}\` → 发版时由总控移动到 `成果区\v{n}\`。
- **临时写入**：先写 `*.tmp`，写完 rename 成正式文件名；禁止让下游读到半成品。

## 4. 静默循环（每个工位强制执行）

> 角色卡里写的"按总纲第 4 节循环"就是这一节。除总控向人类请示外，员工输出任何自然语言都会导致本轮结束、循环断裂。

### 4.1 每轮固定动作

> **用 AIOA 工作台内置监听时**：第 1、2、3、5、7、8 步由监听程序完成
> （读指针、读开关、写心跳、取件、归档、释放锁）；模型只在有文件时被叫醒，
> 拿到当前文件路径，直接做第 6 步。**不要再调用 `wait_for_files` 自己轮询。**
> 外部 AI 窗口没有内置监听，才需要完整执行第 1–8 步。

1. **读指针**：读 `{{ROOT}}\_ACTIVE_PROJECT.md`，取 `root` 作为 `PROJECT_ROOT`。
2. **读开关**：读 `{PROJECT_ROOT}\01_总控\发件箱\_GLOBAL_STATUS.md`。若为 `PAUSED`：
   - 向本工位 `_READY.md` 追加一行 `PAUSED ack {时间}`；
   - 释放锁；
   - **结束本轮，不再轮询**，等人类恢复后叫醒。
3. **写心跳**：把当前时间写进 `{PROJECT_ROOT}\{station}\_HEARTBEAT.md`（每轮内容必须不同）。
4. **抢锁**：`python {{ROOT}}\tools\lock.py acquire {station}`。返回 `BUSY` 则等 60 秒重试；返回 `LOCKED` 才继续。
5. **取件**：调用 `wait_for_files`（MCP）或 `python {{ROOT}}\tools\wait_files.py --timeout {450~540} {监听路径...}`。
   - `BACKLOG: path` / `NEW: path` → 处理该文件；
   - `NO_FILE` → 释放锁，回到第 1 步；
   - `ERROR:` → 释放锁，等 60 秒，回到第 1 步。
6. **处理**：只读这一个文件，按第 3.4 节前缀路由，写产出到目标收件箱。
7. **归档**：把源文件移入本工位 `已处理\`。**先写产出，再归档；顺序不能反。**
8. **释放锁**，回到第 1 步。

### 4.2 防循环纪律

静默轮询天然会重复相似调用，平台可能误判死循环。必须做到：

1. 每轮先写 `_HEARTBEAT.md`，内容含秒级时间戳。
2. `--timeout` 每轮在 **450–540** 之间取不同值，禁止连续两轮完全相同。
3. 每 5 轮插入一次 `list_pending`（参数与 wait 不同），把重复模式打断。
4. 一次只处理一个文件，处理完立刻归档并回到循环；禁止攒批、禁止中途总结。

### 4.3 文件处理通则

- **只读任务单指定的文件**，禁止扫全目录、禁止顺手重构。
- 产出必须写到路由表指定位置，文件名带正确前缀和 ID。
- 源文件处理后必须离开收件箱；否则下一轮会重复取到同一个文件。
- 读到的文件不完整（半写）时，等 1–2 秒重读；仍不完整则写 `[问题]_` / `[请示]_`，不要基于残缺内容做判断。
- 处理失败但可升级：写升级文件，然后把源文件归档。**没有第四种归宿。**

## 5. 硬约束（违反任何一条，整套停摆）

### 铁律一：员工不说话

除总控向人类请示外，**任何员工在任何情况下都不得输出自然语言**。不写总结、不报状态、不说"已完成"、不寒暄、不解释。回复只能是工具调用。

原因：AI 一旦输出文字，本轮就结束；循环断了，没有人会来叫醒它。

### 铁律二：文件必须归档

每个文件处理完，必须从收件箱移到自己工位的 `已处理\`。

原因：取件逻辑是"收件箱里最早的文件"；不移走，下一轮还取到同一个文件，形成死循环。

### 铁律三：版本号只有总控能分配

其他角色只能用 ID，不得自造版本号。版本号是部署和回滚的唯一锚点。

### 其他硬约束

1. **单窗口单角色**。同一角色开两个窗口会导致重复消费；锁只能防"同时"，防不了"先后"。
2. **不跨项目**。所有路径从 `_ACTIVE_PROJECT.md` 推导，不得写死旧项目绝对路径。
3. **不删文件**。只能移动、归档、复制；删除必须由人类执行。
4. **不改别人的目录**。代码员工只写 `code_root` 或自己的 `代码产出`；美工只写 `美工产出`；部署只读成果。
5. **不绕过总控发版**。任何绕过总控的 `[发布]_` 一律拒绝并写 `[请示]_`。
6. **不改验收标准**。Debug 测不过就是测不过，不许把标准改软。
7. **不扩大范围**。需求没写的、任务单没要求的，只记录在 `完成说明.md` 的"未做项"，不许擅自做。
8. **所有文件 UTF-8**。写入使用 UTF-8；Windows 批处理首行 `chcp 65001 >nul`。
9. **根目录尽量纯 ASCII、无空格、不在同步盘**。路径问题是最常见的故障源。
10. **不改协议**。要改先由人类确认，并同步更新角色卡、工具、模板。

## 6. 异常、升级与超时

### 6.1 升级路径

```
代码员工卡住 → [问题]_ → 高级代码
                          ├─ 不改对外行为 → [技术裁决]_ → 代码员工
                          └─ 改对外行为   → [架构升级]_ → 实施布置
                                                            ├─ 授权内 → [技术裁决]_
                                                            └─ 越权   → [请示]_ → 总控
```

- 高级代码必须给**唯一结论**，不许"两个方案都可以"。
- 拿不准是否越权时，按越权处理。
- Debug 同一问题自动修复最多 2 轮；第 3 轮必须 `[修复确认]_`。
- 部署失败最多自行重试 1 次，之后必须 `[部署阻塞]_`。
- 总控送审超时 30 分钟 → `[待人类决策]_`，**不自动放行**。
- 其余环节**故意不设超时**：宁可卡住让人发现，也不要静默丢件。

### 6.2 必须找人类的情况

总控遇到以下任一情况，停下该条线，写 `[待人类决策]_{ID}.md` 并在会话里直接问人类：

1. 产品方向、范围增删、验收基线变更；
2. 两个方案都说得通，现有资料无法判定；
3. 需要外部信息（部署平台、账号、预算、素材、版权）；
4. 实施层连续两轮报同一个阻塞；
5. 不可逆操作（删数据、覆盖存档、对外发布）。

其余情况总控自己裁决，不许拿小事打断人类。

### 6.3 失败处理

- 写文件失败：重试 1 次；仍失败则写 `[问题]_`（技术侧）或 `[请示]_`（策划侧），并归档源文件。
- 监听异常：释放锁，等 60 秒重试；连续 3 次异常写 `[请示]_` 并停止本轮。
- 目录缺失：本工位自检只创建自己的目录；整棵项目树缺失属于总控未启动，其他工位写 `[请示]_` 后停止，不要自行补建。

## 7. 上下班、暂停与恢复

### 7.1 上班

人类在窗口里发「上班。」后：

1. 执行角色卡的启动自检；
2. 删除本工位 `_OFFDUTY.md`（存在则删）；
3. 进入第 4 节静默循环。

### 7.2 下班

人类发「下班。」后：

1. **处理完当前文件**，不要中途丢件；
2. 写 `{PROJECT_ROOT}\{station}\_OFFDUTY.md`，内容含时间与原因；
3. 向 `01_总控\来自实施层` 写 `[待命]_{station}_{时间}.md`（状态：已下班）；
4. 释放锁，停止轮询，不再取新件。

**注意**：只写 `_OFFDUTY.md` 而不发指令，AI 窗口不会自己停；只发指令而不写文件，状态面板看不见。两者要同时做。AIOA 工作台的「下班」按钮会写文件并复制指令。

### 7.3 暂停全部

人类把 `_GLOBAL_STATUS.md` 改成 `status: PAUSED`。员工在**下一轮循环开头**停下，正在处理的文件不会中断。

### 7.4 恢复

1. 把 `_GLOBAL_STATUS.md` 改回 `status: ACTIVE`；
2. **逐个窗口发「继续监听」**——暂停后的窗口不会自己醒；
3. 顺序：`01 → 02 → 04/05 → 03/06/08 → 07`。

### 7.5 切项目

只改 `{{ROOT}}\_ACTIVE_PROJECT.md` 的 `project` / `root` / `status` / `updated` 四行。员工下一轮自动跟过去，不需要重启窗口。目标项目目录树必须已存在。

## 8. 项目档案与代码根

每个项目根有一份 `_PROJECT.md`：

```yaml
name: P001_第一个项目
title: 项目标题
code_root: D:\my-repo\src
deploy_target: Cloudflare Pages
baseline: D:\my-repo\docs\开发总纲_V1.0.md
```

- `code_root` 必须是绝对路径；员工所有代码读写都在它下面。
- `code_root: none` 表示从零新建，代码写 `04_代码员工\代码产出\{ID}\`。
- `deploy_target: 待定` 时，部署环节必然阻塞并上报人类。
- `baseline` 是需求与验收的权威依据；没有就写 `none`，不要猜。

## 9. 自检与维护

### 9.1 每日开机

1. 清残留锁：`python {{ROOT}}\tools\lock.py clear`（确认没有窗口在干活）。
2. 看全局状态：`python {{ROOT}}\tools\pause.py status`。
3. 看工位状态：`python {{ROOT}}\tools\status.py --stale 8`。
4. 看汇报终端有没有 `[待人类决策]_` 或 `[阻塞]_`。

### 9.2 健康标准

- 8 个工位都有心跳（`_HEARTBEAT.md` 时间新）。
- 没有 `⚠️ 卡住`。
- 收件箱积压不持续增长。
- 版本号不跳号、不重复。

### 9.3 定期瘦身

`python {{ROOT}}\tools\tidy.py` 先预览，`--apply` 再执行。只归档、不删除。

### 9.4 故障优先级

1. MCP 未信任 / 路径错；
2. 全局 `PAUSED`；
3. 锁残留；
4. 同一角色开了两个窗口；
5. 文件半写 / 编码错误。

详细处置见 `01_操作手册\04_故障排查.md`。

## 10. 变更规则

### 10.1 加新工位必须改五处

1. `new_project.py` 的 `TREE` 与 `READY_DIRS`；
2. 新角色卡 `09_xxx.md`；
3. 本文件第 3.4 节路由表；
4. `status.py` 的 `STATIONS`；
5. `tidy.py` 的 `STATIONS`。

漏掉第 4、5 项会导致状态面板看不见、归档无限膨胀。

### 10.2 改前缀 / 改落点

必须同时更新：本文件路由表、所有相关角色卡、消息模板、工具脚本、工作台路由配置。改完跑 `smoke_test.py` 和一条真实需求。

### 10.3 原则

- 一次只改一处；
- 先想清楚回滚方式；
- 不许为了"看起来更先进"破坏三条铁律；
- 人类确认后才能动协议。
