# 工作流全景

> 一个需求从进入到上线，会经过哪些手、经过哪些文件、卡在哪里会怎样。
> 看懂这一份，就理解了整套系统。

---

## 一、主干链路（一个需求的一生）

```
 ①人类
   │  写 [需求]_xxx.md
   ▼
 ②总控  ──[审校]_──▶ ③智囊
   │  ◀──[审校意见]_──┘
   │  定稿
   ▼
   [策划]_xxx.md
   ▼
 ④实施布置 ──拆单──▶ [任务]_xxx.md ──▶ ⑤代码员工 / ⑥美工
   │                                        │
   │                                        │ 写代码 / 出图
   │                                        ▼
   │                                   [待测试]_xxx.md
   │                                        ▼
   │                                    ⑦Debug
   │                                  跑验收标准
   │                                        │
   │            ┌───────────────────────────┤
   │            │ 通过                       │ 不通过
   │            ▼                            ▼
   │      [验收通过]_xxx.md            自动修（≤2轮）
   │            │                      或 [修复确认]_
   │            ▼                            │
   │      成果复制到 成果接收\                └──▶ 回 ⑤
   ▼
 ④实施布置 核准 → 成果复制到 成果区\_待发布\
   │  写 [汇报]_xxx.md
   ▼
 ②总控 分配版本号 v{n} → 成果移到 成果区\v{n}\
   │  写 [发布]_v{n}.md
   ▼
 ⑧部署 部署 → [部署回执]_v{n}.md
   │
   ▼
 ①人类 在 汇报终端 看到 上线_v{n}.md
```

---

## 二、每一步的细节

### ① 人类写需求

- **落点**：`01_总控\收件箱\[需求]_{ID}.md`
- **谁取**：总控
- **必须含**：背景、目标、范围、明确不做、可判定的验收标准
- **常见错误**：验收标准写"体验良好" → 智囊会打回，或者 Debug 无法判定

### ② 总控出策划初稿

- **落点**：`08_智囊\收件箱\[审校]_{ID}.md`
- **同时**：在 `01_总控\_PENDING_REVIEW.md` 记一行，在汇报终端写"初稿已送审"
- **关键**：**不能直接发实施布置**。必须等审校意见。
- **例外**：改文案、调参数、修 bug 这类小单可标 `免审` 直发
- **超时**：30 分钟没收到意见 → 写 `[待人类决策]`，**不自动放行**

### ③ 智囊审校（可选工位）

- **落点**：`01_总控\收件箱\[审校意见]_{ID}.md`
- **只查五类**：遗漏、矛盾、不可验收、依赖缺失、口径冲突
- **不查**：文风、排版、你觉得更好的做法
- **只审一轮**：交出去就结束，不接受追问

### ② 总控定稿

- **落点**：`02_实施布置\收件箱\[策划]_{ID}.md`
- **一次性定稿**：合理意见收进去，不认同的写 `[待人类决策]`，不争论、不二次送审
- **必须附**：已采纳 N 条 / 未采纳 M 条

### ④ 实施布置拆任务单

- **落点**：编码 → `04_代码员工\收件箱\[任务]_{ID}.md`；美术 → `06_美工\收件箱\[任务]_{ID}.md`
- **必须含六项**：目标、输入、产出物路径、验收标准、依赖 ID、截止优先级
- **硬规则**：写不出可判定验收标准的任务，不许下派，退回总控

### ⑤ 代码员工实现

- **写在哪**：`code_root`（`_PROJECT.md` 指定）；`code_root: none` 时写 `04_代码员工\代码产出\{ID}\`
- **必附**：`完成说明.md`（做了什么 / 改了哪些文件 / 怎么跑 / 自测结果 / 已知限制 / 未做项）
- **然后**：写 `05_Debug\收件箱\[待测试]_{ID}.md`
- **遇到卡点**：写 `03_高级代码\收件箱\[问题]_{ID}.md`，**停手等裁决**，不要一边等一边改

### ⑥ 美工出图（并行支线）

- **产出**：`06_美工\美工产出\{ID}\` + `效果说明.md`
- **两条通知都要发**：
  - `04_代码员工\收件箱\[适配]_{ID}.md`（要接入代码）
  - `02_实施布置\收件箱\[交付]_ART_{ID}.md`（要核准）
- **规格不明**：不猜，写 `[架构升级]_` 要求补规格

### ⑦ Debug 测试

- **报告**：`05_Debug\测试报告\{ID}.md`（用例、实际结果、结论）
- **通过**：
  1. 成果复制到 `02_实施布置\成果接收\{ID}\`
  2. **必须写** `02_实施布置\成果接收\[验收通过]_{ID}.md` ← 不写这个，实施布置永远等不到
  3. 写 `05_Debug\成果移交\{ID}.md`
- **不通过（可自动修）**：直接修，最多 2 轮，经验写 `经验库\`
- **不通过（需设计确认）**：写 `[修复确认]_` 给代码员工

### ④ 实施布置核准

- 核对成果是否覆盖任务单**全部**验收项
- 复制到 `01_总控\成果区\_待发布\{ID}\`（不删原件）
- 写 `[汇报]_{ID}.md`（批次、包含任务、变更点、已知风险）
- **不写版本号**

### ② 总控发版

- `_VERSION.md` +1
- 成果移到 `01_总控\成果区\v{n}\`
- 写 `07_部署\收件箱\[发布]_v{n}.md`
- 写汇报终端 `进度_v{n}.md`

### ⑧ 部署

- 从 `成果区\v{n}\` **只读**拉取
- 成功 → `07_部署\部署报告\部署_v{n}.md` + `01_总控\来自实施层\[部署回执]_v{n}.md`
- 失败 → `[部署阻塞]_v{n}.md`，最多重试 1 次

### ② 总控收尾

- **`[部署回执]_` 只归档**，写汇报终端 `上线_v{n}.md`
- **禁止再发 `[发布]_`** ← 发了就无限重复部署

## 三、三条支线（不打断主干）

### 支线 A：技术问题升级

```
代码员工 卡住
  │ 写 [问题]_
  ▼
高级代码 判定
  │
  ├─ 不改变对外行为 ──▶ [技术裁决]_ ──▶ 代码员工按裁决改 ──▶ 重新 [待测试]_
  │
  └─ 改变对外行为 ──▶ [架构升级]_ ──▶ 实施布置
                                        │
                                        ├─ 授权内 ──▶ [技术裁决]_
                                        └─ 越权 ──▶ [请示]_ ──▶ 总控裁决
```

**关键**：高级代码**不写代码**，只出决策文件。它给的是唯一结论，不是"你们商量"。

### 支线 B：验收不过

```
Debug 测不过
  │
  ├─ 可自动修（≤2 轮）──▶ 自己修 ──▶ 复测 ──▶ 通过则走正常流程
  │
  └─ 第 3 轮 / 需设计确认 ──▶ [修复确认]_ ──▶ 代码员工改 ──▶ 重新 [待测试]_
```

**关键**：同一问题自动修复最多 2 轮。第 3 轮必须升级，防止 Debug 无限改下去。

### 支线 C：美术与代码并行

```
实施布置
  ├──[任务]_──▶ 代码员工 ──▶ [待测试]_ ──▶ Debug ──▶ [验收通过]_ ──┐
  │                                                                  │
  └──[任务]_──▶ 美工 ──┬──[适配]_──▶ 代码员工 ──▶ [待测试]_ART_ ────┤
                       │                                            │
                       └──[交付]_ART_──────────────────────────────┤
                                                                    ▼
                                                            实施布置 合并核准
```

**关键**：美术和代码是两条并行支线，在实施布置的 `_待发布` 汇合。
美术的 `[适配]_` 会让代码员工多跑一轮接入测试。

## 四、谁卡住会怎样

| 卡在哪 | 现象 | 系统行为 |
|---|---|---|
| 智囊没起 | `[审校]_` 躺在收件箱 | 30 分钟后总控写 `[待人类决策]`，该线暂停 |
| 实施布置没起 | `[策划]_` 躺着 | 无限等。**没有任何超时机制** |
| 代码员工没起 | `[任务]_` 躺着 | 无限等。同上 |
| Debug 没起 | `[待测试]_` 躺着 | 无限等。同上 |
| 部署没起 | `[发布]_` 躺着 | 无限等。同上 |
| 总控没起 | 所有上游产出都堆在 `来自实施层` | 整个系统停摆 |

**设计取舍**：只有"送审"有超时（因为智囊是可选的），其余环节**故意不设超时**——
自动超时会导致任务被跳过而没人知道。宁可卡住让你发现，也不要静默丢件。

**所以 `status.py` 的"⚠️ 卡住"是主要发现手段。** 每天跑一次。

## 五、时间预期（参考值，不是承诺）

| 环节 | 正常耗时 | 说明 |
|---|---|---|
| 需求 → 策划初稿 | 2–10 分钟 | 取决于需求复杂度 |
| 初稿 → 审校意见 | 3–15 分钟 | 智囊读两份文件 + 逐条比对 |
| 意见 → 定稿 | 2–5 分钟 | 有分歧则暂停等人类 |
| 策划 → 任务单 | 3–10 分钟 | 拆得越细越慢 |
| 任务单 → 代码完成 | 20 分钟–数小时 | 取决于任务量 |
| 代码 → 测试报告 | 10–40 分钟 | 取决于验收项数量 |
| 测试 → 核准 → 发版 | 5–15 分钟 | 两跳 |
| 发版 → 部署回执 | 5–30 分钟 | 取决于平台 |

**一条中等复杂度的需求，从投递到上线，大约 1–3 小时。**
这个时间主要由 AI 的思考速度决定，不是由你的操作决定——投完就可以走开。

## 六、状态机（每个文件的三种归宿）

```
收件箱\xxx.md
   │
   ├──▶ 处理成功 ──▶ 产出写到目标收件箱 ──▶ 源文件移入 已处理\
   │
   ├──▶ 处理失败/需升级 ──▶ 写 [请示]_ / [问题]_ / [架构升级]_ ──▶ 源文件移入 已处理\
   │
   └──▶ 无法处理（规格不明）──▶ 写 [架构升级]_ 要求补规格 ──▶ 源文件移入 已处理\
```

**没有第四种归宿。** 任何"放着不动"都是 bug——会让 `wait_for_files` 每轮返回同一个文件，
形成死循环。

---

## 七、文件数量守恒

每处理一个文件，系统净增：

- 至少 1 个产出文件（到下游收件箱）
- 1 个归档文件（源文件进 `已处理\`）
- 可能 1 个台账/心跳更新

所以**收件箱深度不会无限增长**——只要每个员工都归档。
如果某个收件箱持续增长，说明那个工位卡住了或窗口挂了。

**监控方法**：

```bash
python tools\status.py --stale 15
```

`积压` 列持续 > 0 且 `最后活动` 越来越久 = 卡住。
