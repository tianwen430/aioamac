## 0. 一句话结论

**标准模式永远不可改**（8 工位模板只读）；想自定义，就**复制一份**，在复制出来的
配置里做有限改动：核心 4 人（01/02/04/05）固定，03/08 是开关，06/07 不带，
新增自定义角色最多 3 个；用户随便填的"任务草稿"**必须经过一次规范化**
（配置态 AI 单次调用）才能上岗；所有改动先过校验，再生成协议和角色卡。

**角色卡不是作文，是岗位合同。能改的只有"职责契约"层，承重墙（骨架）永远由系统生成。**

## 1. 背景与要解决的问题

### 1.1 为什么现在的 8 工位不可配置

当前"8"写死在多处：

| 位置 | 写死了什么 |
|---|---|
| `main/workflow.js` | `STATIONS`（8 定义）、`TREE`/`READY_DIRS`、需求固定投 01、归档/自检遍历 8 |
| `02_协议总纲.md` | 目录树、路由表、循环规则 |
| `03_工具/*.py` | `install.py`/`status.py`/`smoke_test.py`/`tidy.py`/`new_project.py` 按 8 个工位写 |
| 渲染层 | `STATION_ORDER` 固定排序 |

只换角色卡**不解决**问题：AI 会按旧协议路由投递，收件箱可能根本不存在。
所以配置化必须"角色卡和协议一起生成"。

### 1.2 要解决的三个用户痛点

1. **新手怕麻烦**：上来 8 个窗口、8 张卡、逐个上班bye，吓退陌生人。
   → 自定义模式默认走**工作台内置监听**（工作台自己就是工位窗口）。
2. **怕 AI 改坏流程**：让模型自由写卡，写不全，还会把路由/归档/静默纪律改掉。
   → 三层角色卡 + 受控职责包 + 硬校验。
3. **Token 成本担忧**（老板原话："每读一圈好像都要有 token"）：
   外部窗口模式确实每圈都烧；内置监听空转 0 token，处理文件才花。
   → 详见第 8 节 Token 预算与优化。

## 2. 产品模型

### 2.1 两种模式

| | 标准模式（默认） | 自定义模式 |
|---|---|---|
| 来源 | 内置 8 工位模板 | 从标准模板**复制**并按配置生成 |
| 可改性 | 全只读（协议/卡/目录树都不许改） | 仅"工作流级开关 + 新增角色" |
| 数据位置 | 工作流根目录 | 独立根目录（不污染标准模板） |
| 数量 | 1 | **最多两套**并存，可导出/导入 |
| 定位 | 出问题好排查的兜底 | 实际生产用 |

自定义模式只允许两类改动：

1. **结构开关**：03（技术裁决）、08（顾问审校），见 2.5；
2. **新增自定义角色**：上限 **3 个**，见 2.6。

其余角色（01/02/04/05）**职责、路由、目录全部锁死**；04 默认职责锁定，
要不同类型的执行者就新增员工型自定义角色（见 3.3 决策）。

### 2.2 锁分级

| 级别 | 范围 | 规则 |
|---|---|---|
| L0 | 协议核心不变量：静默循环、前缀机制、归档/锁/心跳、`_GLOBAL_STATUS` | 任何模式不可改 |
| L1 | 01 总控、02 实施布置的职责与路由；04/05 的骨架 | 锁死；AI 模型可自由换（本来就应该能换），显示名用系统别名 |
| L2 | 自定义工作流的结构开关（03/08）；06/07 是否带入 | 表单/开关控制 |
| L3 | 自定义新增角色（≤3）：职责包字段 + 补充说明 | 用户填草稿 → 规范化 → 校验 → 写入 |

### 2.3 角色卡三层（自定义角色适用；标准模板整卡只读）

| 层 | 内容 | 来源 | 用户可改？ |
|---|---|---|---|
| ① 固定骨架 | 身份行、工位目录、收件箱、产出目录、启动自检、静默循环、归档/锁/上下班、路由段、硬约束、静默纪律 | 系统按配置生成 | **不可** |
| ② 职责契约 | 职责名称、输入前缀、输出前缀、工作目录、完成标准、升级(上报)条件、工具权限、禁止事项 | 从**职责包**实例化（AI 规范化产出） | 可（经校验+diff确认） |
| ③ 补充说明 | 工作风格、行业背景、偏好 | 用户自由填 | 可（≤300 字，卡内标注"非规范性，不得覆盖①②"） |

这样即使③写得离谱，流程仍按①②跑，最差是产出质量差，不出现系统性故障。

### 2.4 角色别名表（写死在系统里，禁止 AI 改名）

路由、目录、配置永远用 ID（`01`~`08` + 工位目录名）；显示层用别名。
协议与角色卡首行统一写成「01 总经理（总控）」这种格式。

| ID | 目录 | 别名 | 中文定位 | 自定义模式 |
|---|---|---|---|---|
| 01 | 01_总控 | **总经理** | 项目总控与最终裁决 | 固定 |
| 02 | 02_实施布置 | **总监** | 排期/切割/核准，中间管理者 | 固定 |
| 03 | 03_高级代码 | **部门经理** | 技术裁决与升级分流 | **开关** |
| 04 | 04_代码员工 | **员工** | 执行与问题提交 | 固定 |
| 05 | 05_Debug | **质检** | 测试与复核 | **固定（必须有复核）** |
| 06 | 06_美工 | **设计** | 视觉产出 | 标准版保留；自定义不带 |
| 07 | 07_部署 | **运维** | 发布部署 | 标准版保留；自定义不带 |
| 08 | 08_智囊 | **顾问** | 给 01 的策划稿做补充审校 | **开关（向导默认开）** |

> 06/07 为什么不进自定义：它们是**任务型角色**——只在有对应任务时被唤醒，
> 内置监听下空转 0 token，留着几乎不花钱。自定义模式不带它们，
> 但对应任务（美术/部署）也不会有处可去，属"明确不支持"，而不是悄悄失败。
> 标准版 8 人照旧保留。

### 2.5 结构开关（03 / 08）

**开关改的是"建不建岗位 + 路由表"，不是让用户改协议。** 联动全部由系统自动完成。

向导预填（已拍板 D13/D15）：**08 默认勾开、03 默认不勾**（提示文案本身就写着
「简单任务建议关闭」）——新手打开向导看到的就是 5 人组（01/02/04/05 + 08），
不额外做任何"默认态判断"分支；03 想要再手动勾上。

#### 关 03：「启用 03 部门经理（技术裁决）？简单任务建议关闭」

| 动作 | 内容 |
|---|---|
| 岗位 | 不创建 03 目录与角色卡 |
| 02 的卡 | 自动挂载**「技术裁决」职责包（强制，撤销不了**）：判断问题的技术性，给 `[技术裁决]_` 裁决文件 |
| 路由 | `[问题]_`：04 → **02**（原为 →03）；02 回 `[技术裁决]_` → 04 |
| 为什么强制 | 撤掉后 `[问题]_` 只能报到 01，越级且 01 变垃圾场——"那就没有意义了"（老板原话） |
| Token | 02 单次调用变重（多背裁决段），总账通常下降 |

#### 关 08：「启用 08 顾问（审校）？关掉后策划稿由 01 自审定稿」

| 动作 | 内容 |
|---|---|
| 岗位 | 不创建 08 目录与角色卡 |
| 01 的卡 | 删 `[审校意见]_` 段；自动挂载**「自审清单」职责包**（来源：08 的审校职责） |
| 路由 | 01 出 `[策划]_初稿` → **自审 → 定稿 `[策划]_` → 02**；不再有 01↔08 往返 |
| Token | 01 单次调用变重、少一轮交接；总 token 通常更低 |
| 待定 | 向导里 08 的默认值（开还是关），见 §13 |

#### 循环轮次影响（老板关心的"循环 Token 会不会涨"）

- 关 08：01 少一次"送审→收意见→定稿"往返，**轮次变少**；
- 关 03：冲突只发生在 04 提问题时，轮次在处理内部差异（03 一决 vs 02 顺带决），
  大致持平；
- 结论：开关对轮次的影响远小于"协议变厚"的影响，控制厚度的手段见 §8。

### 2.6 职责包（结构化"任务"，不是一句话）

**"明天让代码员工去买图"不是角色卡该管的事**——那是任务单（`[任务]_xxx.md`）。
角色卡里能改的长周期职责，一律建模为职责包：

```json
{
  "id": "visual-production",
  "name": "视觉生产",
  "stationType": "worker",
  "stationDir": "06_美工",
  "inputs": ["[任务]_ART_"],
  "outputs": ["[交付]_ART_"],
  "workDir": "美工产出",
  "criteria": [
    "每个任务单都有对应的效果说明",
    "资源清单、切图清单、命名规则、接入要求四项齐全",
    "产出目录中不出现未在清单里声明的文件"
  ],
  "escalate": ["需求缺视觉规范", "资源格式无法满足", "连续两次被退回"],
  "tools": ["read", "write", "edit", "search"],
  "forbidden": ["修改代码文件", "绕过 02 直接发给 04"],
  "draft": "……用户原文（规范化前保留）",
  "status": "normalized"          // draft → normalized → active
}
```

字段规则：

- `inputs/outputs` 必须使用**已注册前缀**（见 §7 校验）；新前缀由系统在角色创建时
  分配（如 `[任务]_安全_`），不允许 AI 自造新机制；
- `criteria` 必须可判定：「当…时，…必须…」句式；"很好地完成""尽量做好"
  在规范化阶段被 AI 直接重写，继续出现则校验标黄；
- `stationType` 仅允许 `worker`（员工型）与 `task-type`（设计/运维型，走标准 06/07 职责包）；
- 新增角色的工位目录用**代号标记**（D14）：`A01_<名字>`、`A02_<名字>`、`A03_<名字>`
  （上限 3 个恰好对应 A01~A03；每套自定义工作流内部从 A01 递增，第二套独立根目录、
  代号重新从 A01 起，套间互不冲突）；角色卡与协议角色索引沿用同代号。
- 保存时展示**改写前后 diff**，用户确认才写盘；写入只用原子替换 + 备份，
  且只写角色卡②层，①层由生成器重铸。

## 3. 数据模型：`_AIOA_WORKFLOW.json`

安装根目录新增一份拓扑描述文件；**生成器、投递、内置监听、状态页、CLI 全部读它**。

```json
{
  "schema": "aioa-workflow/1",
  "name": "四人小队",
  "derivedFrom": "standard@8",
  "entry": "01",
  "root": "D:\\ai-workflow-4p",
  "switches": {
    "tech_review": false,          // 03 部门经理
    "advisor_review": false        // 08 顾问
  },
  "stations": [
    { "id": "01", "dir": "01_总控", "alias": "总经理", "card": "02_角色卡/01_总控.md",
      "inboxes": ["收件箱"], "outputs": ["已处理", "发件箱"], "order": 1 },
    { "id": "02", "dir": "02_实施布置", "alias": "总监", "card": "02_角色卡/02_实施布置.md",
      "inboxes": ["收件箱", "来自实施层"], "outputs": ["已处理", "发件箱"], "order": 2 },
    { "id": "04", "dir": "04_代码员工", "alias": "员工", "card": "02_角色卡/04_代码员工.md",
      "inboxes": ["收件箱"], "outputs": ["已处理", "代码产出"], "order": 3 },
    { "id": "05", "dir": "05_Debug", "alias": "质检", "card": "02_角色卡/05_Debug.md",
      "inboxes": ["收件箱"], "outputs": ["已处理", "测试报告", "成果移交"], "order": 4 }
  ],
  "routes": [
    { "prefix": "[需求]_",       "from": "human", "to": "01" },
    { "prefix": "[审校意见]_",   "from": "01", "to": "01", "skip": true },
    { "prefix": "[策划]_",       "from": "01", "to": "02" },
    { "prefix": "[任务]_",       "from": "02", "to": "04" },
    { "prefix": "[任务]_ART_",   "from": "02", "to": null, "note": "自定义模式无 06，禁用" },
    { "prefix": "[待测试]_",     "from": "04", "to": "05" },
    { "prefix": "[验收通过]_",   "from": "05", "to": "02" },
    { "prefix": "[问题]_",       "from": "04", "to": "02", "note": "关 03 时 02 挂技术裁决" },
    { "prefix": "[技术裁决]_",   "from": "02", "to": "04" },
    { "prefix": "[发布]_",       "from": "01", "to": null, "note": "自定义模式无 07，禁用" },
    { "prefix": "[请示]_",       "from": "*",  "to": "01" },
    { "prefix": "[汇报]_",       "from": "*",  "to": "01" }
  ],
  "customRoles": [
    // 示例：{ "id": "a01-archive", "name": "资料管理", "stationDir": "A01_资料管理", … }
  ],
  "capabilities": { "dispatch": true, "plan": true, "execute": true, "verify": true },
  "createdAt": "2026-11-03T00:00:00.000Z"
}
```

要点：

- `routes` 是唯一路由事实源，协议总纲的路由表**由它生成**（不再是手写文档）；
- 03/08 开关直接体现为 `stations` 与 `routes` 的增删 + 对应职责包挂载；
- 新增角色 = `customRoles` 里挂职责包 + 该工位目录（自动编号 `A01+`）；
- P1 实现沿用现有安装布局：角色卡放**控制层根目录**（如 `01_总控.md`、`A01_角色一.md`），
  未新建 `02_角色卡/` 子目录；`card` 字段只存文件名，便于与既有标准安装兼容；
- `capabilities` 用于校验必需能力存在（接单/规划/执行/验收）。

## 4. 配置态向导（用户操作全流程）

> **配置态不是运行状态**，它是一次性配置向导：安装向导 + 单次模型调用 + 校验 + 写盘，
> 结束即退出。运行态的 01 总控**不参与润色**，不背着配置指令（否则每轮调用白涨 token）。

```
工作流页「新建自定义工作流」
  ↓
1) 起名 + 选根目录（默认 ~/ai-workflow-custom-<名字>）
  ↓
2) 结构开关：
   ┌ 核心四人组（01 总经理 / 02 总监 / 04 员工 / 05 质检）——固定，不可减
   ├ ▢ 03 部门经理（技术裁决）   ⚠提示：简单任务建议关闭；关闭后 04 的问题直接报 02，02 自动接管裁决
   └ ▢ 08 顾问（审校）           ⚠提示：关闭后策划稿由 01 自审定稿，不再送审
   快捷组合不做多套预设（老板拍板"不搞那么复杂"）：预填就是 5 人组（08 开、03 关），想改手动勾
  ↓
3) 新增自定义角色（0~3 个）：选用途类型（执行型 / 设计型 / 运维型 / 资料&运营型）
   + 「任务内容草稿」随便写；目录与显示名系统自动分配「A01 角色一 / A02 角色二 / A03 角色三」
   （先不支持改名，D18）；目录代号套内递增
   ※ 自定义工作流**最多两套**：已有两套时「新建」置灰，提示先删除或导出其中一套
  ↓
4) 点「规范化去写」→ 配置态：
   - 全局状态置 CONFIGURING，所有内置监听暂停
   - 一次模型调用：草稿 → 职责包 JSON（P2 实现；P1 先用表单手填）
     ※「规范化」的合格标准 = 通过 §6 校验：P1 手填结构化表单同样算规范化；
       P2 上线 AI 润色后，只是把"填表"换成"润成再填"，最终都以过校验为准。
   - 校验 + diff 预览，用户确认/退回重改（可多轮，但仍按"次"计）
  ↓
5) 生成：目录树、00_协议总纲.md（含路由表与角色索引）、8+N 张角色卡（骨架+职责包实例）、
   汇报终端、tools、_mcp_config.json、_READY 收集
   - 全程原子写 + .bak 备份
  ↓
6) 干跑自检（目录/卡/路由一致性 = smoke 等价物），通过 → 恢复运行态
  ↓
7) 引导：为每个工位"新建对话 → 选模型 → 顶部「监听」"（内置监听默认）；
   也可导出角色卡文本给外部窗口（可选）
```

草稿规范化的产物**不是整张卡**，而是职责包（§2.6）。规范化失败（AI 输出不合格 schema）
不允许直接用草稿上岗——**没有"跳过规范化"选项**（老板拍板：草稿必须规范化）。

## 5. 生成器：协议与角色卡怎么"长"出来

### 5.1 协议总纲（生成而非手写）

结构（控制在 ~2k tokens）：

```
00_协议总纲.md
  ├ 核心不变量（固定段，来自标准协议，逐字复用）
  ├ 路由表（由 routes 生成）
  ├ 角色索引（ID | 别名 | 目录 | 输入前缀 | 输出前缀 —— 一行一角色）
  └ 循环规则（固定段）
```

**总纲不放任何单个角色的职责细节**——细节在各自卡里。01 的上下文 =
核心协议 + 路由表 + `_GLOBAL_STATUS` + 当前文件，**不随角色数线性膨胀**。

### 5.2 角色卡（生成而非手写）

每张卡 = 固定骨架模板 + 职责包实例化：

- 01/02：骨架 +〔接单/规划/裁决…固定职责〕+（关 08 时）自审清单包
  +（关 03 时 02 挂）技术裁决包；
- 04：骨架 + 执行职责（默认锁定=代码实现）；05：骨架 + 测试复核职责（锁定）；
- 新增角色：骨架（按类型模板）+ 用户职责包 + ≤300 字补充说明段。

**开关变化时不是重写全卡，只是增删预生成段落**（已与老板确认过机制）。

### 5.3 配套

- 汇报终端、投递需求下拉、上下班按钮、`_READY` 收集、状态自检全部读 `_AIOA_WORKFLOW.json`；
- `tools/*.py`（status/tidy/new_project/smoke_test/lock/pause）改为**读同一配置文件**
  （`install.py` 仍是 pip 安装工具，本期不改，见 P3）。

## 6. 校验规则（保存/安装前全跑，任何一条不过就不许装）

1. 每个路由前缀**有且只有一个**接收方；

## 7. Token 预算与优化

### 7.1 先纠正一个说法（老板对了一半）

| 模式 | 空转 | 处理文件 |
|---|---|---|
| 外部窗口自主循环 | **每圈一轮模型调用**：读心跳、查收件箱、写心跳，全烧 | 更贵 |
| 工作台内置监听 | 程序取件，`NO_FILE` 不叫模型，**空转 0 token** | 照样花（协议/卡/任务/历史） |

老板体感"每读一圈都要 token"在外部窗口模式**完全正确**；内置监听只是把空转砍掉，
**处理单价没变**，且历史越滚越长会让单价涨。

### 7.2 单次处理调用的费用构成

```
每次调用 ≈ 协议核心/角色卡（稳定） + 各类状态（半稳定） + 当前任务 + 历史（增长）
```

粗算（现标准 8 人）：协议+卡 5~8k tokens；一天 50 个文件 ≈ **25~40 万输入 token/天**（未含历史）。

### 7.3 优化清单（按优先级）

| # | 措施 | 期 | 预期效果 |
|---|---|---|---|
| 1 | **心跳/收件箱/观察全部程序化**：监听循环自己更新 `_HEARTBEAT.md`、查收件箱；模型只在有文件时被叫醒，直接拿到路径 | P2 | 空转成本归零（已内置于现有监听，需补"心跳程序写"） |
| 2 | **协议分层 + 分级读取**：启动读一次全文；循环只读 `_GLOBAL_STATUS` + 当前任务；规则变更/异常才重读协议 | P2 | 每次调用减 2~5k |
| 3 | **稳定前缀前置**：协议/角色卡放系统提示最前，动态状态放后——吃到服务商 prompt cache | P2 | 重复输入折价 |
| 4 | **历史压缩**：同一对话每处理 N 个文件，摘要旧轮次，只留最近几条 + 当前任务 | P3 | 涨势封顶，长任务省 30~60% |
| 5 | 配置指令（润色角色卡能力）**单独放 `01_总控_配置态.md`**，不进运行卡 | P2 | 运行态不背配置负担 |
| 6 | 循环节奏分级（04/05 快、01/02/03/06/07/08 慢） | **未来再说**（老板原话） | 只影响延迟，不省 Token |

注意优先级反直觉点：**关 08 不是省审校，是把审校并回 01**——01 单次略重，
但少一轮交接+上下文，总账通常降。真正省钱的杠杆是 #1~#4，不是开关。
